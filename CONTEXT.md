# Architecture context

Orientation for engineers and coding agents new to JellyPlay. User-facing feature docs live in `docs/`; this file is about how the code is shaped. The KMP migration (docs/kmp-migration-plan.md) is COMPLETE: every feature lives in `shared/feature/*` (commonMain + platform actuals), the core stack in `shared/core/*` (former legacy modules' Android halves are now `androidMain` source sets of `:shared:core:ui` / `:shared:core:data`, identical packages, Robolectric suites in their `androidHostTest` lanes), and the only Android-only module left is the `:app` shell, beside `apps/desktop`. Persistence is Room 3 (`androidx.room3`) on android/jvm. DI is Koin-only repo-wide.

Player code lives in two shared modules: `shared/core/player-contract` (engine-agnostic `MediaEngine` contract + engine-shared machinery) and `shared/feature/player-video` (VOD player screen, ViewModel, session collaborators). Package↔module anomaly (recorded decision): ALL of player-contract's commonMain declares the `com.raulshma.jellyplay.feature.player.video.engine` package (zero import churn when the contract split out of the feature); three contract files borrow other packages — `PlayerLifecycleCallbacks` + `RemotePlayableEngine` borrow `core.data` packages, `SessionPositionStore` keeps the canonical `feature.player.video` package (moved verbatim so the shared `FakePositionStore` test double satisfies it without a core→feature edge). Grepping by package cannot tell module; the dependency edge that matters is recorded in `shared/core/player-contract/build.gradle.kts`. New player-contract files keep the contract's canonical feature package. `EngineStateChassis` (published flow fields, reset choreography, updateConfig dedup guard, buffer capacities as ctor params) is contract commonMain; `BasePlayerEngine` (player-video androidMain) and `MpvDesktopEngine` extend it — a new published flow is declared once. Both shells register nav sections through one aggregator module, `shared/feature/shell` (`appSections` + `ShellHostHooks` + a registration ledger the desktop dead-end guard derives from). Paths below are relative to the repo root.

## Engine layer

- **`MediaEngine`** (player-contract commonMain `engine/MediaEngine.kt`): the single strategy interface every playback backend implements — `ExoPlayerEngine`, `MpvPlayerEngine`, `LibVlcPlayerEngine`, `NoOpEngine` (external playback) under player-video androidMain `engine/`. Deliberately ONE wide contract (load/`PlaybackRequest`, reactive `StateFlow`s, tracks, capabilities via `EngineCapabilities`, config via `updateConfig(EngineConfig)`); a previous role-interface split delivered no decoupling.
- **`PlayerEngineFactory`** (player-video commonMain): maps `PlayerType` → engine. Process-wide Koin single so the shared Media3 `DefaultBandwidthMeter` (adaptive-bitrate learning) survives across streams; `resetBandwidthMeter` is the test/diagnostics escape hatch.
- **`EngineEventCoordinator`** (player-contract commonMain): owns the engine-event *policies* for BOTH players — guarded play/buffering mirrors, transcode-fallback policy, the 20 s buffering watchdog, subtitle toasts, pass-out protection. Decision model: one `EngineEventSource` per engine instance carrying the minimal `isPlaying`/`playbackState`/`errors`/`subtitleEvents`/`currentPositionMs` slice (`MediaEngine.toEngineEventSource`; the live tuner engine feeds its own instance mapping `LiveEngineState`→`EnginePlaybackState`) → `EngineDecision`s (`ShowError`/`FallbackToTranscode`/`PlaybackEnded`/`PassOutPause`/`InformUser`) on a tryEmit-only `SharedFlow`. Never writes uiState, never commands the engine; every policy assertable with flow fixtures + injected clock (commonTest suite). Hosts pin historically-different behavior via `Config` knobs: the VOD `PlaybackSession` constructs/re-arms/executes the defaults (`FallbackPolicy.FORCE_DIRECT_PLAY_ONE_SHOT` — latch re-armed by `onNewItem`/`onPlaybackModeChanged` — and `WatchdogScope.INITIAL_BUFFER_ONLY`), VM collects mirrors only; `LiveTvPlayerViewModel` passes `WatchdogScope.EVERY_BUFFERING_EPISODE` (a stalled tuner can stall MID-playback without an exception) and `FallbackPolicy.EXTERNAL_REQUEST_ONLY` (the tuner engine's per-load phase machine decides WHEN fallback fires, unlatched) and executes decisions itself.
- **`EngineSessionShell`** (contract commonMain `engine/`): session-structural plumbing both hosts construct instead of hand-wiring the coordinator's lifecycle/event machinery — construction over the host's hot engine-source stream, `dispose`/`reArm`, decision fan-out TaskBundle slot. Hosts: `PlaybackSession` (VOD), `LiveTvPlayerViewModel` (live). Pinned by `EngineSessionShellTest`.
- **`PlayerChromePolicies`** (contract commonMain `chrome/`): pure chrome-timing policies BOTH player screens cite: `controlsAutoHideTimeoutMs` (TV-doubling fold over each screen's preference-sourced base), `liveWindowRefreshLoop` + `LIVE_WINDOW_REFRESH_TICK_MS` (live DVR-window poll — the live engine contract is media3's PULL model, so a poll cadence is unavoidable; gated on the auto-hiding chrome being visible), `mirrorPlaying(source, sinks)` (same-value guard, then ORDERED positional fan-out — the uiState write must precede collaborator forwards; sinks are idempotent mirrors; the one lifecycle-attached member, returns its `Job`), the seek-step family `seekBackTargetMs`/`seekForwardTargetMs`/`stepSeekTargetMs` (live's ±10 s math rides the same 0-floor + duration cap — a live FIX, its inline seeks had none), `shouldScheduleControlsAutoHide` (the shared predicate with constant-false for chrome concepts live lacks), and `shouldRestoreHostWindowOnDispose(currentlyInPip)` (shared PiP-dispose gate both screens run; live previously lacked it entirely).
- **`BasePlayerEngine`** (player-video androidMain): shared boilerplate base for the three reloadable adapters — the 8 `StateFlow`/`SharedFlow` backing fields, main-thread `engineScope`/`mainHandler`, `updateConfig` dedup guard, polling/stats setters, the published-state RESET choreography (`resetItemScopedPublishedState` + `onResetItemScopedState` per-engine hook; `resetPublishedEngineState` adds playbackState→IDLE, isPlaying→false), and the Activity pause/resume template (`onActivityPause`/`onActivityResume` with `onPausedNative`/`onResumingNative` hooks absorbing native quirks). Each adapter keeps its native handle, native track/subtitle application (common fold rides `MpvTrackCatalog`/`MpvSubtitleSideLoadPlan`), stats projection, `positionFlow` wiring. `NoOpEngine` does NOT extend it.
- **`ReloadablePlayerEngine`** (player-video androidMain, extends `BasePlayerEngine`): second layer — `PlaybackSnapshot`/`withPreservedPlayback` (position+speed+isPlaying across a rebuild), volume/mute commands delegated to commonMain `VolumeCommandTemplates` over one `NativeVolumeSurface` seam, the `callbackFlow` + `EnginePositionTicker` shell for `positionFlow`, `EngineVideoStats` change-guard. `snapshotIsPlaying` hook covers snapshot and current checks (Exo overrides to read `player.isPlaying` synchronously).
- **`EnginePositionTicker`** (contract commonMain): the shared polling-ticker loop every `positionFlow` uses — bounded paused-wait (`POSITION_PAUSED_RECHECK_MS = 2_500L`), play↔pause edge detection, `delay(pollingIntervalMs)`, all in one place. `primeFirstTick` primes one synchronous `onActive` read inside `launch()` (UNDISPATCHED, caller's thread — a dispatched first tick could race the stop-report fallback it feeds). BOTH audio managers pass `primeFirstTick = true` (idempotent through dedup-guarded flows); the video adapters keep it OFF (their `callbackFlow` shells already prime via initial `trySend`). Pinned by `EnginePositionTickerTest`.
- **`PlaybackVolumePolicy` / `AspectRatioMapping` / `EngineDurationFallback`** (player-video commonMain `engine/`; `MpvStyleMapping` itself lives in player-contract commonMain): the adapters' pure decision halves — volume/mute plans (clamp, remember-unmute, `MediaStreamVolume` sync, `0.05f` floor; per-engine max boost as declared data: nominal 1.0f, VLC 2.0f — declared divergence, not copy variance), per-engine aspect plans (Exo resize-mode, mpv panscan + subtitle margins, VLC aspect-string; CROP is a *declared* native-frame reset on VLC — libVLC 3.x exposes no engine-drivable zoom), duration→server fallback ladder. Adapters only apply plans. The volume/mute half is ONE commonMain template: `VolumeCommandTemplates` (player-video commonMain) owns the four `MediaEngine` commands as `final` templates (plan → remember → capture → native write → system-stream mirror) over the `NativeVolumeSurface` seam — `readNativeVolume` (null aborts delta templates), `applyNativeVolume`, `volumeBoostCeiling`, `nativeVolumeRestore(muted)` (policy's `NativeVolumeRestore` vocabulary: Exo ZERO/FULL, mpv LEAVE_UNCHANGED, VLC ZERO/REMEMBERED_LEVEL), `applyNativeMuteFlag` (mpv's real flag), `muteTemplateEnabled` (VLC null-handle abort), Android-only system-stream sync, desktop-only user-change capture. BOTH Android finals and desktop `MpvDesktopEngine` delegate here; remember unified BEFORE the native write. Pinned by `VolumeCommandTemplatesTest`; `PlaybackVolumePolicyTest`/`AspectRatioMappingTest`/`EngineDurationFallbackTest` pin all three engines. `PlaybackVolumePolicy` is public only because the protected `nativeVolumeRestore` seam returns its nested enum — not a stable API.
- **`PlayerLifecycleManager`** (core:data jvmShared `playback/`): Activity↔engine lifecycle bridge — `onActivityPause`/`onActivityResume` delegate straight to the `@Volatile activeCallbacks` engine ref (set by `PlayerSessionManager` on create/release; no StateFlow hops). Pausing skipped when background-audio is enabled in `PlaybackStore`.
- **`MpvErrorTaxonomy`** (player-video commonMain): one errorCode→`EngineError` table (−13 LOADING_FAILED→Network; −14…−19 init/format family→Decoder; else Unknown) + the Android string-code normalization (`fromCodeString`). Declared divergence: the Unknown arm's diagnostic — desktop `mpv_error_string(code)`, Android the raw handed-over string. Pinned by `MpvErrorTaxonomyTest`.
- **`MpvEventFold`** (contract commonMain `engine/mpv/`): the one raw-mpv-event → engine-state fold both mpv engines apply — the `MpvPlaybackLatches` latch set (isPlaying fileLoaded/eof-gated — Android formerly wrote it unguarded from the pause observer), cue clears (desktop's clear-on-`sid`-switch arm), track re-enumeration, the live-subtitle mirror, the END_FILE error signal. Pinned by `MpvEventFoldTest`.
- **`MpvTrackCatalog` + `MpvSubtitleSideLoadPlan`** (same `engine/mpv/`): the shared track-republish half — the pure track-list→`MediaTrack` catalog both mpv engines funnel `buildTracks` through, and the `sub-add` side-load plan whose registry stamps the caller's `SubtitleSource.id` onto the republished tracks. Side-load id contract pinned per platform by `MpvTrackCatalogTrackSelectionContractTest`.
- **`CueAccumulator.mergeAccumulatedCues`** is public (shared merge rules; desktop's private mirror deleted — it keeps only its `sub-start` read divergence at the call site). Pinned by `CueAccumulatorTest` for both platforms.
- **`MpvFoldApplier`** (contract commonMain `engine/`): the one fold-APPLICATION body both mpv engines ride (latch resets, END_FILE error-emission-before-apply ordering) over two narrow sinks (`refreshTracks(reason)`, `onLiveSubtitleLine`); Android's `refreshReason` passthrough is the applier's second apply parameter. Standardized the live-subtitle order to Android's accumulate-then-mirror (declared unification — the ops are independent). Riding the same pass: `MpvSubtitleSideLoadPlan.applyBatch` (plan → registry store-back → per-add loop; transport spellings per host), `MpvTrackCatalog.trackEntry(raw)` (the ONE track-list normalization over the plain map both transports produce — Android's residue is a 4-line `MPVNode.asPlainValue` flattener), `MpvTrackCatalog.existingSubtitleLabels` (raw-title extraction; fixes Android's dead label-dedupe which compared display labels). `TrackRefreshCoalescer` moved to contract and went public; the desktop ADOPTS coalescing (~80 ms debounce — intended behavior change). The remaining known twin was EVENT INTAKE (Android `MPV.EventObserver` vs desktop `registerObservers`/`handleEvent`); a wide `MpvBinding` interface was REJECTED — the narrow-surface pattern is the repo's seam idiom, and the twin is since unified at the DECISION level by `MpvPropertyIntake`. Pinned by `MpvFoldApplierTest`, the catalog suites, and the parity suite.
- **`MpvPropertyIntake` + `MpvIntakeHost`** (contract commonMain `engine/mpv/`): the ONE mpv property-change → decision table both engines funnel observer callbacks through — the property-INTAKE half of the `MpvEventFold`/`MpvFoldApplier` unification. Pure `(host, property, value, context) → decision`: each host's reader translates its native payload into the binding-agnostic `MpvIntakeValue` union (Android typed event overloads, desktop memory reads) and calls `MpvPropertyIntake.dispatch`; a result is an `MpvPlaybackEvent` (folding through the applier) or a raw cache sink. Per-engine divergence is a DECLARED row (`MpvIntakeHost` enum is the per-engine column): the buffered-math pair (Android `cached position + demuxer-cache-duration` vs desktop `demuxer-cache-time × 1000`; desktop does not observe the duration property), Android's registered-but-dropped `speed`, Android's debug-log `sub-visibility`, desktop-only channel-count, Android-only `sub-start`. Engines keep THIN reader funnels (pointer shapes, null-payload coercions, released guards stay reader-side); non-property events (START_FILE/FILE_LOADED/END_FILE/IDLE) fold through `MpvEventFold`. Pinned by `MpvPropertyIntakeTest` (commonTest — every row with representative values, BOTH buffered formulas, host gating, unknown/wrong-shape nulls).
- **The desktop mpv engine rides the same commonMain policies**: `MpvStyleMapping` is PUBLIC in player-contract commonMain beside `MpvSubtitleStyleApplier` + `MpvStatsProjection` (one apply choreography + one stats property table both engines ride) — subtitle styling is one mapping for both platforms. `AspectRatioMapping.mpvPlan` and `EngineDurationFallback` went PUBLIC (desktop is a separate Gradle module — `internal` visibility was exactly why the desktop kept drifted bodies): the aspect plan writes the 4-property set incl. `sub-use-margins`/`sub-ass-force-margins`, `resolveDurationMs` replaces the desktop's inline ladder (desktop `stop()` resets `serverDurationMs` like Android), `selectTrack` carries Android's arm set (negative-index `aid`→"auto", `sid`→"no", `sub-visibility` re-enable — the desktop's raw `"-1"` write was rejected by mpv; positive-path int-then-string write discipline). Desktop unmute now restores the remembered level into the mpv `volume` property (desktop has no system music stream, so the property IS the audible surface). Each fix pinned by `MpvDesktopEngineAndroidParityTest` (real-libmpv headless). Observer registration + event thread start moved to a late `init` block (construction-race fix: mpv's queued observation backlog cannot fold over still-null member state).
- **The media3 narrowing is a typed capability, not a cast**: `RemotePlayableEngine.underlyingPlayer: Any?` is RETIRED (the contract keeps only control members). androidMain's `Media3PlayerHost` capability interface (`media3Player: Player?`, implemented by `ExoPlayerEngine`) plus `MediaEngine.asMedia3Player` is the SINGLE narrowing site (the `ZoomSafeSubtitleStrategy` precedent: declare a capability on the seam instead of type-testing concrete adapters). `MediaSessionController.createForPlayer` takes the typed `MediaEngine?` (no-op when no media3 player); `createForBackgroundCast(sessionId)` resolves the cast receiver's player behind an androidMain-wired provider. player-video's `CastManager` seam dropped `castPlayerForSession`; the legacy core:data member feeds `VideoMediaSessionFactory`'s provider wiring directly.

## Playback session (`PlaybackSession`)

**`PlaybackSession`** (player-video commonMain) is the "deep module" behind `VideoPlayerViewModel`; one instance owns a playback session's lifecycle:

- **initialize** — ordered load entry: latch resets, remote "Play On" routing early-return, same-item short-circuit, single-flight `loadJob`, mini-player reclaim, and WHEN `SessionLoadPipeline` starts.
- **retry / reload / decisions** — `retryWithEngine`, `retryPlayback`, `reloadForMode`, `reloadForStreamChange`, plus the `EngineEventCoordinator` lifecycle and decision fan-out. Every engine-adopting path outside `SessionLoadPipeline` rebinds through ONE funnel, `rebindSessionTracking(itemId, trackProgress = true)` (reload ×4, retry, reclaim); cinema pre-roll intros call it with `trackProgress = false` (not library history). Pinned (reclaim trio + cinema suppression).
- **reporting + release** — stop reports deduped via a per-session latch; `getReportPositionMs` seek latches; release split: session-owned teardown half first, then the ViewModel half back-to-back from the same synchronous call chain (no dispatch hop — an interleaved recomposition could flash a stale title).
- **position persistence** — process-death resume behind the `SessionPositionStore` seam (`SavedStateHandlePositionStore` wraps 4 `SavedStateHandle` keys; positions older than 1 h are stale and ignored).
- **cinema intro** (`beginCinemaMode`/`advanceCinemaIntro`) and the **mini-player reclaim body** (`loadReclaimedEngine`).

The session **never touches `VideoPlayerUiState`** — every uiState read/write is a constructor lambda or a `SessionLifecycleHooks` hook; outcomes surface as `SessionEvent`s (`ShowError`, `InformUser`, `PlaybackEnded`, `ClosePlayerRequested`, `PassOutPause`) on an `events` `SharedFlow`. The ViewModel is the single forwarder; autoplay/close policy stays VM-side.

**`PlaybackSession`** (player-video commonMain) is the player's composition root — the ONE place the collaborator graph is constructed and armed (absorbed the deleted two-phase `PlayerWiring` builder, which had itself replaced the VM's ~1,400 lines of in-class wiring AND the deleted `VideoSessionHost` pass-through layer). Cycles die by OWNERSHIP now, not late binding: the six write-once `...Ref` slots (`mediaDetailProjectionRef`, `playbackSessionRef`, `episodeContinuationRef`, `playbackPreferenceWriterRef`, `engineConfigSyncRef`, `playerSessionManagerRef`) are gone — the session constructs its collaborators in dependency order inside its own composition, and each former cycle's late fact (reporter ids, cinema handoff, stream-change reload) flows through an internal seam the owning collaborator controls. The session implements `SessionLoadOutputs` + `SessionLifecycleHooks` itself and wires `SessionLoadHooks` at its construction site. VM-facing split: the session owns the graph and the uiState-write lambdas through the sanctioned `SettingsProjector` pair (the ONE sanctioned state-transformer exception, see `ControllerOwnershipTest`); the ViewModel keeps constructor deps, state holders, the `onEvent` funnel + handlers, expose-only flows. Host behavior funs live with their halves: `fetchMediaSegments`/`shouldAttemptCinemaMode`/`restoreRememberedMuted` in `SessionLoadPipeline`, `reportPlaybackStart` in `PlaybackSession`. Pinned by `PlaybackSessionCompositionTest` + moved pins in `SessionLoadPipelineTest`/`PlaybackSessionReportingTest`; tests construct the graph via `PlaybackSessionTestGraph` (jvmTest). A full PlaybackStack wrap stays REJECTED: both `PlaybackSession` suites construct the session WITHOUT the VM via the deliberate half-interface split (KDoc at the interface) — the session composition keeps that property. The live `LivePlaybackSession` keeps its own zero-lambda shape (deliberate divergence).

**`EngineAttachController`** (player-video commonMain) owns the engine-attach choreography: bind → style seed (BEFORE anything below can rebuild an engine config, no suspension between) → capabilities mirror → effects seed → cast strategy → delay notice → PiP hasNext → `onEngineRecreated` (before the tracks collector) → three child collectors (availableTracks, currentCues, playbackState→SyncPlay+PiP auto-exit). ONE public `attach(engine)`; re-attach cancels previous collectors; job dies with the VM scope. Zero uiState-type references. Pinned by `EngineAttachControllerTest` (9 cases incl. exact-order call log). `SessionLifecycleHooks` is the VM-bound synchronous prologue (transport re-arm, new-item resets, routing gates, VM teardown half, trickplay clear, SyncPlay reattach), implemented by `PlaybackSession`. `sessionState`/`engineFlow` are direct aliases of `PlayerSessionManager`'s flows — same instance, dispatch ordering unchanged.

The VM's three playback-pref setters (`setPlaybackMode`, `setStreamingQuality`, `setAdaptiveBitrateEnabled`) funnel through one private `applyPlaybackPrefChange(mode, quality, persist)` — guard/coordinator/mirror-write stay per-setter, the command owns launch → persist → reload with EXPLICIT post-change values; `reloadPlaybackForMode` no longer reads the ui-prefs mirror back. Pinned at the session seam.

**`PlayerStores`** (player-video commonMain) is the construction-time store bundle (the `HomeStores` move): the twelve datastore stores the player reads/writes (`aggregate` VideoPlayerAggregateStore, `engine` PlayerEngineStore, `subtitleLanguage` SubtitleLanguageStore, `playback` PlaybackStore, `audio` AudioStore, `audioEffects` AudioEffectsStore, `videoPlayer` VideoPlayerStore, `security` SecurityStore, `syncPlayCast` SyncPlayCastStore, `downloads` DownloadsStore, `appearance` AppearanceStore, `networkOffline` NetworkOfflineStore) arrive as ONE `stores: PlayerStores` aggregate — a new store dependency widens the bundle + the two platform Koin definitions, not the VM interface and every call site. NOT a read-only narrowing: the VM keeps every store command write, and members flow through to the internally-built modules under their ORIGINAL receiving parameter names (deep modules' signatures untouched). A `HomeRefresherFactory`-style construction factory was evaluated and REJECTED — every remaining parameter is a runtime input, a directly-touched collaborator, or a single-module pass-through the VM deliberately shows in one place (`ControllerOwnershipTest` pins declaration order). `PlayerStores` is PUBLIC (unlike home's internal `HomeStores`) because `VideoPlayerViewModel` is public.

**`EpisodeNavigator`** (player-video commonMain) owns episode navigation: season/episode browsing writes (through a single `updateEpisodes` seam), adjacent-episode discovery, and previous/next choreography — the #146 single-flight latch (held until the session settles on a different non-null item, an error, or `NEXT_EPISODE_SETTLE_TIMEOUT_MS`), mark-played-on-advance (incognito gate rides the VM's `onAdvanceFrom` lambda), and SyncPlay queue routing (VM lambdas encapsulate the group-queue check). **`EpisodeContinuationController`** (player-video commonMain) is the VM-owned constructor-lambda controller holding the episode-continuation cluster: the `EpisodeNavigator` stack, the `markWatchedAndSkip`/`markUnwatchedAndQuit` orchestration (incognito routes the mark to the offline-local record and skips the unwatched one; "watched & skip" reuses `playNextEpisode` so latch and group routing apply), the autoplay-cancel wiring behind the Up Next overlay (decision clock THEN overlay mirror, in that order — a cancelled countdown can never auto-advance), and the smart-download cleanup. Every fact the moved logic read from the VM arrives as a narrow constructor lambda — no raw `VideoPlayerUiState` handle crosses; `ControllerOwnershipTest`'s migrated-controllers ratchet: 13 after this extraction, 19 after `StillWatchingController` + `MediaDetailProjection` (which added the `videoPlayerViewModel_totalLineCeiling` size ratchet — 3_015 wc-lines), 20 after `EngineConfigSync` (runtime engine-config rebuild + drag-settling debounce via `EngineConfigBuilder.buildFromSlices`; VM ceiling now 1_752).

**`PlayerKeyPolicy`** (beside `PlayerScreenPolicies`) keeps `mediaKeySeek` (per-key seek step/direction rows) and the delay-shortcut steps (`delayAdjustMs` over the shared ±30s clamp), consumed by `handleMediaKeyDown`. ## Direct Play ↔ Transcode

`PlaybackMode` (core:model) is `AUTO` / `FORCE_DIRECT_PLAY` / `FORCE_TRANSCODE`. With **AUTO** the server decides via PlaybackInfo against the device profile and the effective max bitrate resolved by **`AdaptiveBitrateManager`** (core:data): quality tiers (360p–4K), a 2.5 Mbps cap on metered networks, data-saver clamping, a manual cap; with adaptive bitrate disabled the cap is `null` and the server direct-plays anything decodable. **FORCE_DIRECT_PLAY** requests the "direct play all" profile — the server hands back a static URL even for codecs the device cannot decode; when that fails at runtime, the coordinator's one-shot fallback latch emits `EngineDecision.FallbackToTranscode`, and the session flips the mode to FORCE_TRANSCODE (persisted via `PlaybackStore`), stop-reports the old session and reloads. **FORCE_TRANSCODE** makes the server re-encode; `reloadForMode` surfaces a "Switched to transcoded stream" notice. When the server transcodes, `TranscodeReasonsRefresher` fetches the live session's `TranscodingInfo` reasons; they land in `PlayerSessionState.transcodeReasons` and are mirrored into `uiState.media.transcodeReasons` by the ViewModel's sessionState collector (`isDirectPlayForced` mirrors the mode the same way).

## Session identity

**`HomeSession`** (core:data jvmShared `session/`) is the identity module. The atomic session source is the network engine: `JellyfinApiEngine.session` publishes `ActiveSession?` — one server plus its authenticated user as ONE value, updated inside the engine's critical sections — so observers never see the synthetic `(newServer, oldUser)` intermediate that combining the separate `currentServer`/`currentUser` StateFlows produces during a two-step publish. Derived corollary: never re-derive "is there a session" by combining those two flows. `AuthRepositoryImpl.isAuthenticated` is `apiClient.session.map { it != null }` (`WhileSubscribed(5_000)`, initial `false`) for exactly this reason. HomeSession classifies consecutive identities from the session flow into `HomeSessionTransition`s — `SignedIn`, `UserSwitched`, `ServerSwitched`, `SignedOut`, each carrying `previousIdentity` (null only on `SignedIn`) — collapsed by `distinctUntilChanged`, and exposes the sanctioned identity reads for cache keying: `cacheIdentity` (suspend, reads the SOURCE flow) and `cacheIdentitySnapshot` (synchronous mirror read, for best-effort evictions where staleness is benign). `HomeViewModel` subscribes to `transitions` directly for its scroll-reset/refresh choreography.

**`SessionCacheRegistry`** (core:data commonMain `session/`) is the single home for identity reactions. It owns the ONE collector on `HomeSession.transitions`; anything that must react to an identity change registers instead of writing a bespoke collector: `registerCaches(owner, caches...)` for plain `TtlCache`s whose wholesale clear is the whole reaction, `registerAction(owner, action)` when the reaction is more (the action receives the transition, so it can read `previousIdentity` — Media's persisted home-section SWR clear needs it). `SignedIn` never triggers; every other transition clears the registered caches then runs the actions in registration order, each per-owner failure caught and logged so one bad owner cannot kill the stream; registration is idempotent per owner. Registered owners: `media` (MediaRepositoryImpl's TtlCaches + its `media-identity-clear` action: `DetailCacheGroup.invalidateAll` + the previous identity's SWR room rows), `episode-catalogue` (an action — `invalidateAll` also bumps the in-flight epoch), `playback` (the media-segments cache), `seerr` (the detail cache).

## Deferred user-data freshness

**`DeferredUserDataRefresher`** (core:ui `viewmodel/`) is the read-side twin of the silent flip contract: a user-data change landing while a screen is NOT shown only MARKS it stale (boolean `pendingRefresh` — a WS burst collapses to one refresh), and the single regeneration fires on the next `onScreenActiveChanged(true)`. A change landing while the screen IS active arms the flag but never regenerates mid-scroll — the pager-generation swap the contract exists to prevent only ever happens on re-entry, when the grid rebuilds from the top anyway (`getRefreshKey` anchors within one generation, it does not carry the anchor across). It is itself a `DeferredRefreshHost` (`DeferredRefreshEffect(viewModel.deferredRefresher)` is the whole screen wiring). Main-thread confinement: the collector and the `LifecycleResumeEffect` caller both run main-immediate. **Silent-failure re-arming**: a host whose regeneration failed WITHOUT surfacing an error (the stale-while-revalidate paths) calls `rearm` so the next re-entry retries. Cancellation never re-arms (the cancelling loud load is the regeneration).

The host choreography (collection/person/album detail) is one shape, owned by **`DeferredFetchCoordinator<K, T>`** (core:ui) — a state-container owner, not just a job-slot owner. The host hands ONE aggregate-returning fetch — `suspend (id: K, force: Boolean) -> T`, throwing on failure — and the coordinator owns `state: StateFlow<DeferredFetchState<T>>` plus the entire loud/silent publish policy: loud accepted publishes Loading synchronously on the COORDINATOR's state (the hosts' screen-facing state is a projection that trails one hop, each host's KDoc declares it); loud failure publishes Error while KEEPING the last value (all-or-nothing on the loud path); silent success serves stale-while-revalidate without ever touching `isLoading` (the pull-to-refresh spinner keys off it); silent success over a failed loud load HEALS the error with no Loading flash. `FetchMode`, the old `Boolean` protocol, and the `onLoudStart`/`onLoudError`/`onSilentHeal` hooks are gone. `load(id, force = false)` is the loud entry; the coordinator tracks what that id's last completed fetch did, which IS the back-stack re-entry guard the hosts used to hand-roll: a loud load for the id already showing whose last fetch succeeded is a no-op, a previously failed one re-arms. `updateValue(transform)` is the host-side optimistic-patch seam; it patches whatever value is kept — including one behind an in-flight loud reload's spinner, where the completing load's aggregate overwrites it. `force` bypasses the guard and reaches the fetch body as the repository cache-bypass flag. The single-flight/re-arm table: one fetch-job slot for loud AND silent loads — a loud load cancels an in-flight silent one (re-arming first), the deferred refresh skips itself while any load is active (the skip re-arms), any fetch reporting failure re-arms, cancellation never re-arms. The fetch invocation is wrapped in `runCatchingRethrowingCancellation` (core/ui depends on :shared:core:concurrency for it) — a cancelled loud load cannot mask as a fetch failure and strand its spinner. Throwables that are not `Exception`s (an `Error`) are not fetch failures either: `runFetch` rethrows them. Pinned by `DeferredFetchCoordinatorTest`; the migrated hosts' suites pin only their projection surfaces. The whole-screen hosts' Loading → Error → content precedence is one shared fold, `DeferredFetchState.wholeScreenPhase`. **`MusicHomeViewModel` rides it too (the chassis split is closed)** — its loud fetch publishes PARTIAL sections (sub-fetch failures drop rows while the load still reports failure for the re-arm), needs quiet failures (offline gate, swallowed partials), and clears its error only past the offline gate: all three need the mode inside the fetch body, which the state-container interface deliberately removed. The VM adapts with `Unit` (no subject id — every loud entry forced) and recovers the loud/silent split from the phase the loud entry publishes: `uiState.isLoading` is written synchronously in `loadSections` BEFORE `load` launches, and the fetch body reads it at entry as the loud marker. The partial-publish policy is preserved inside the body; quiet failures re-arm through `DeferredUserDataRefresher.rearm` themselves. The frozen `LegacyDeferredFetchCoordinator` verbatim copy is deleted.

Data side: the #157 lazy-staleness rule lives in **`StaleReadGroup`** + **`StaleReadGroups`** (core:data jvmShared `concurrency/`, beside `SingleFlightFetcher`). One `StaleReadGroup` owns the whole ladder for one read group: arm on announce → `staleAwareRead(force) { effectiveForce -> … }` consumes the marker as a one-shot force (forced reads consume it too — such a read is at least as fresh as the announce) and re-arms on BOTH failure shapes (returned `Result.failure` and thrown, cancellation included — the two fixed bug classes). `MediaRepositoryImpl` holds a registry of three — `homeSectionsStale`, `albumTracksStale`, `collectionItemsStale` — declared at construction via `register(ridesUserDataWrite = …)`. Arming fan-out is registry-owned: `announceConfirmedWrite` (every confirmed own-write path — flips, delivered STOPs, the outbox drain, via the synthetic `notifyUserDataChanged`) arms ALL THREE; `announceUserDataWrite` (the USER-DATA callers of the composite eviction) arms only the two gap groups (registered `ridesUserDataWrite = true`) — NOT inside `invalidateUserDataCaches` itself, because that eviction also serves `invalidateFor(ALBUM)` from every FORCED album-detail read, and a pull-to-refresh must not arm markers. That gap-group arming is deliberately UNCONDITIONAL — it rides the eviction, not the write's confirmation (the local mirror already reflects the staged position on an offline STOP; the outbox drain's later announce is the confirmed half); both divergences cost at most one redundant forced read. A TRACK flip evicts `tracks_<trackId>` and never the album's `tracks_<albumId>` key; a collection MEMBER flip evicts `detail_<itemId>` and never the collection's page keys, so the album's track rows and the collection's pages heal on their next non-forced read. `getMediaDetail` deliberately has NO group: its announce path already eagerly evicts the item's detail entry, so the next read is a guaranteed fresh miss. Adding a fourth group is one `register` call. `StaleReadGroupTest` pins the ladder. `PlaybackRepositoryImpl`'s segments cache follows the same registry doctrine: identity reaction = plain wholesale clear PLUS a registered action that bumps `segmentsEpoch`, so an in-flight previous-identity fetch cannot write back into the just-cleared cache. Server WS pushes arm none of these — `HomeRefresher` serves those live.

The DURATION half of "how stale?" lives in **`FreshnessCeilings`** (core:model commonMain, beside `HomeFreshness` and `TtlCache`): one named constant per NON-home cache policy, cited by each owning site — `FOLDERS_TTL_MS` (10 min), `LATEST_MEDIA_TTL_MS` (2 min), `DETAIL_TTL_MS` (2 min; the detail cluster, collection-items page cache, AND `EpisodeCatalogueImpl`'s series snapshots), `PHOTO_URLS_TTL_MS` (5 min), `SEGMENTS_TTL_MS` (5 min), `SEERR_TTL_MS` (60 s), `ADMIN_SYSTEM_INFO_TTL_MS`/`ADMIN_ITEM_COUNTS_TTL_MS` (2 min each), `MEDIA_INFO_SERVER_NAME_TTL_MS` (30 min), `FAVORITE_FLAGS_TTL_MS` (15 min). All values byte-identical to the private literals they replaced.

## Concurrency (`shared/core/concurrency`)

**`:shared:core:concurrency`** (commonMain, zero-dependency leaf below core:network) is the repo's one cancellation-safety seam. **`runCatchingRethrowingCancellation`** is THE sanctioned wrapper for any best-effort `runCatching` around suspend calls: stdlib `runCatching` captures `CancellationException` and masks structured cancellation — the recurring bug class. Non-suspend bodies (JSON/enum parses in mappers) keep stdlib `runCatching`. **`BareRunCatchingRatchetTest`** (module `jvmTest`) is the source ratchet: bare `runCatching` inside `suspend fun` bodies never increases — the guard is repo-complete, and its guarded-root set is DISCOVERED, not hand-listed (parses every `include(...)` in `settings.gradle.kts` and walks `shared/` + `apps/` for `build.gradle.kts` dirs; a new module is guarded the moment it exists). Baseline runs at the two KDoc'd deliberate entries (HomeDiscoveryStore's best-effort migration swallow, PluginConfigViewModel's asset read); lower the baseline when another site converts, never raise it. The heuristic can't see bare `runCatching` inside suspend LAMBDAS; a review pass converted the two found that way, and the blind spot holds two benign occupants (pure in-memory parses the house rule allows). The doctrine covers the `catch (e: Exception)` twin too, which masks cancellation exactly like bare `runCatching` and is invisible to the ratchet: the `CancellationException`-rethrow arm leads the general arm in `EditorViewModel`, `DownloadSidecarCore`, and `MediaCleanupScanCore`; `SearchViewModel`'s filter persist writes ride `runCatchingRethrowingCancellation` outright. **`TaskBundle`** is the cancel-and-replace slot choreography (named keys over a caller-owned scope; deliberately NOT thread-safe — the same dispatcher-confinement contract as the plain `Job?` vars it replaces). **`FetchGovernor`** is the temporal-policy home beside the choreography primitives — the deadline / single-flight / cadence triple. **`withDeadlineMs`** is the envelope: `withTimeoutOrNull` semantics — the value inside `deadlineMs`, `null` on expiry, the caller's own cancellation propagating untouched (below the envelope there is ONLY OkHttp's per-call read timeout, which a half-open socket defeats). **`SingleFlight.inFlight(key)`** is keyed mutual exclusion: same-key callers serialize (queue-and-run — no coalescing, no supersession; "run only if not already running" is a different policy deliberately absent here), different keys never block, not reentrant, entries live forever (bounded key spaces only). The lock table is born — empty, complete — inside the `SingleFlight` val itself, so a coroutine launched from an init block can never observe an uninitialized lock (the shipped EPG crash class: a bare `Mutex()` field raced its own declaration line on Main.immediate). **`boundedPoll(PollSpec)`** is the cadence: a null attempt CONSUMES the round (the busy-server rule — "busy, try later" is a completed round, not a free retry), the interval gap follows every null attempt but the last (no trailing delay), and the spec carries the whole-poll envelope, backoff factor/cap and jitter. Retry is NOT owned here: per-attempt retry stays in core:network's `RetryPolicy` — an envelope or a cadence wraps a retrying call, never the reverse (the retry must see the deadline's cancellation to give up). Adopters: `EpgViewModel`'s `GUIDE_FETCH` serialization, `ServerHealthMonitor`'s probe, `AdminApiClientImpl.pollForNewBackup`, `ServerDiscoveryService`'s scan window, `HomeRefresher.cappedForcedFetch` (the 30 s going-online cap), `SyncPlayManager.discoverCreatedGroup`; `TimeSyncManager` deliberately NOT adopted (JVM-hard clock + stop-flag semantics). Pinned by `FetchGovernorTest`.

## TV drawer and focus wiring

`TvNavigationDrawer` (app `navigation/`) filters its folder rows through `isExcludedTvDrawerFolder`: the `EXCLUDED_DRAWER_TYPES` collection types (including `livetv`, whose UserView duplicates the drawer's primary Live TV item) plus the DVR recordings library Jellyfin injects with no collection type and the exact name "Recordings". ## Playback focus (ADR-0004)

**`PlaybackFocus`** (core:data commonMain `playback/focus/`) is the ONE owner of cross-player exclusivity — "who is playing, and who must pause whom". Interface: `claimState` (Idle / Held / Suspended) + `acquire`/`release`. The matrix (`PlaybackFocusMatrix`) is pure and total over the closed `PlaybackSurfaceId` world; rulings: newest-wins, a per-row loss directive (`FocusLossDirective.Pause | Duck(volume)` — pause-only by default; VIDEO is the one Duck row, and only while the injected video pref asks), manual-resume (the `playWhenReady` guard makes that true at the OS level: the music surface's `pause` clears playWhenReady, and music has no media3 focus stack of its own — the module's seat is abandoned at release and `Regained` is ignored on pause rows, so nothing can resurrect it).

`DefaultPlaybackFocus` is the commonMain executor; `FocusArbiter` (OS seat — `AndroidFocusArbiter`, one AudioFocusRequest per attributes identity, AUDIOFOCUS_GAIN, no delayed gain) and `PlaybackSurface` (commandable victims AND suspended holders) are the two ports, EACH with two production adapters: `FocusArbiter.request(attributes, listener)` takes the claimant's `FocusAudioAttributes` (matrix rows via `attributesOf` — READ_ALOUD keeps USAGE_MEDIA+CONTENT_TYPE_SPEECH, MUSIC→MUSIC, VIDEO→MOVIE), the desktop in-process `DesktopFocusArbiter` grants vacuously, and `DesktopAudioQueueManagerSurface` gives desktop music the same `onPlayingEdge` claim chokepoint Android music has (Denied mirrors to a pause). Desktop binds `DefaultPlaybackFocus`; `NoopPlaybackFocus` remains for tests. Music's play edge HONORS `acquire`'s outcome: on `FocusOutcome.Denied` (a displaced holder Suspended under an OS loss — e.g. read-aloud during a phone call) the manager pauses instead of producing audio the interface forbade. The reader claims/releases around the read-aloud session and pauses its loop on a displaced `Held`. On Android, music's OS leg is the module's — `handleAudioFocus` is off on BOTH music players (primary and crossfade secondary; built-in handling would fight the seat and let the secondary's GAIN request focus-loss-pause the primary mid-fade), MUSIC claims the seat on the play edge with the MUSIC attributes row, and OS losses on the holder are ENFORCED (`Regained` stays ignored — resume is manual). VIDEO claims through the same matrix on the play edge via `VideoPlaybackSurface` (+`FocusCommandTarget`) and releases on pause/stop (the closed world is complete — `isGrantable(VIDEO)=true`, the OS leg runtime-gated by the `VideoFocusPolicyInput(osLegEnabled, duckOnTransientLoss)` pref seam — `pauseOnAudioFocusLoss=false` = publish-state-only, no OS seat; transient loss DUCKS a held video claim and a regain restores, permanent loss still suspends+pauses, duck stays Held; `PlayerAudioLifecycle` and `Media3LivePlayerAudio`'s legacy path are DELETED — becoming-noisy lives in `AndroidVideoPlayerBecomingNoisy`/`Media3LivePlayerAudio` — and `EngineConfig.pauseOnAudioFocusLoss` is removed, ExoPlayer's `handleAudioFocus` forced off like music's). Deliberate semantic delta: regain after a *pause* ruling stays manual-resume (module law) where ExoPlayer-builtin handling used to auto-resume. See docs/adr/0004-playback-focus.md (+ addendum).
